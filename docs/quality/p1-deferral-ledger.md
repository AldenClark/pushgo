# P1 closure ledger

This ledger closes the governance gap in design gate 21.2 without pretending that a planning row is product evidence. The source of truth for product behavior remains the executable result described by `capability-coverage.md`; every row below records only the **remaining** P1 scope that has not yet reached that evidence level.

The 130 P1 rows in design section 25 are grouped only where they share a user-purpose area, execution lane, accountable role and completion checkpoint. `Design scope` uses a stable section plus inclusive first/last capability title: a new P1 outside those semantic ranges fails the machine check, while ordinary edits earlier in the document do not create bookkeeping churn. A due date is a closure deadline, not a promise that the capability passed. When it expires, the static quality check fails until the capability is evidenced, explicitly re-planned with a reviewable reason, or removed as unreachable product scope.

`DEFERRED` means the residual scope is deliberately outside the current P0-first execution slice. It must never be summarized as `PASSED`, and it cannot satisfy a Release gate whose own P0/P1 requirement is due.

## Operating rule

1. Close the highest-value positive Oracle inside an existing fixture/journey first; add a new UI method or startup only when ownership, lifecycle or system consumer is genuinely different.
2. A group may move from `DEFERRED` only when every referenced P1 row is either backed by a fresh executable receipt or explicitly removed/waived with product rationale. Partial evidence is recorded in `capability-coverage.md`, not promoted here.
3. A due-date edit must state the newly learned dependency or capacity fact in the same change. Repeatedly moving dates without new evidence is a failed gate, not progress.
4. Physical/provider/signing prerequisites remain honest `BLOCKED/NOT RUN`; their deadline makes the missing resource visible but cannot turn simulator or contract evidence into a real-system pass.
